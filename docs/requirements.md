# Foil requirements

## 1. Summary

Foil is a lightweight command-line tool for running a fleet of CLI coding
agents in tmux. A human works with their own agent session. When a task
grows, that session runs `foil seat join lead` and becomes the fleet's
*lead*, in the middle of its conversation. The lead spawns worker agents
from role templates, directs them, and integrates their work, and
`foil seat leave` gives the session back. A lead Foil launches in tmux
is the other way, for a goal that runs while nobody is in the
conversation. Each launched seat runs its harness CLI headless, one
turn at a time: Foil's runner starts a turn when mail or a room post
for that seat arrives, and Foil never types into a pane. Agents talk
through short messages and shared files. Anyone can peek at an agent's
screen, but Foil never interprets what it shows. The workers do the
project work, never the lead.

## 2. Glossary

| Term | Meaning |
|---|---|
| Caller outside the fleet | A `foil` command run with no `FOIL_SEAT_ID`: the human, the human's own agent, or a joined lead. |
| Joined lead | The human's own agent session after `foil seat join lead`. It is the fleet's `lead` seat, with no window. Foil never launches it, hosts it, or types into it. Its `foil` commands run outside the fleet and act as `lead`. |
| Fleet | One running group of seats for a project. A project has one copy of the code. Several fleets may run at once. They share the effective roles, harnesses, and mapping: packaged, then global, then project. Each fleet has its own board, posts, registry, and an optional pair-list override. |
| Seat | One agent session whose runner has its own tmux window, or a joined lead, which has none. |
| Lead | The one seat allowed to spawn and kill other seats: a joined lead, or a seat Foil launched from the `lead` template. |
| Worker | Any seat that isn't the lead. |
| Template | A role profile: a description, a persona, a worktree flag, and a permission mode. The profiles are one list. The default harness and model for each role are a second list. Global is the settings. A project file is an optional whole-role or whole-list override. A fleet file is an optional pair list. |
| Harness preset | How to launch one agent CLI (for example `claude` or `codex`), including the model ids that CLI accepts. The presets are one list. |
| Board | A shared folder all seats can read and write, holding mail, room threads, notes, and contract files. |
| Mail | A message to one seat, stored as one file on the board. A launched lead's mail to `user` goes to the human's mailbox. Mail from `foil` is a fact Foil reports, such as a seat that died, and counts only when Foil recorded it under the fleet's `run/` (F14). |
| Room | A thread of files under that fleet's `board/room/<id>/`, opened with a purpose and a list of members by the lead or by a caller outside the fleet. A post wakes the room's members and the seats it names as `@name`, except a member whose last file there is a decline. The lead changes the members and closes the room. |
| Turn | One run of a seat's harness CLI. The first turn runs the preset's `start` argv with the first prompt; each later turn runs its `turn` argv with the seat's session id and a wake prompt. A turn ends when that process exits (F43). |
| Runner | The Foil process in a launched seat's tmux window. It runs that seat's turns one at a time, shows their output raw in the pane, and records whether a turn is running and how the last one ended (F43). |
| Wake | New mail or a room post for a seat. A launched seat's runner starts the next turn with a wake prompt that lists the new files. A joined lead hears through `foil mail wait` (F41). Nothing is typed. |
| Note | An unaddressed shared file on the board (the notepad). |
| Contract | A board file with an agreed, versioned format. |
| Memory | Reviewed lessons for the project. They outlive fleets and are given to every new seat. Fleet memory is separate: it belongs to one fleet and can name the harness and model list to use for a role from the next spawn on. |
| Peek | Printing the raw last lines of a seat's pane. |

## 3. Workflow

```text
human ──▶ their own agent session
             │  foil init · foil seat join lead
             ▼
          lead (joined, no window) ── foil mail wait ◀── mail, room posts, notices
             │  foil seat spawn · foil send · foil post
             ▼
        ┌──────────── tmux: one fleet ─────────────┐
        │  implementer-1   implementer-2            │
        │  reviewer-1                               │
        └───────────────────────────────────────────┘
             all seats read/write the board
```

1. The human works with their own agent. When a task grows, the human
   asks it to bring in a fleet.
2. The agent runs `foil init` once per project, then
   `foil seat join lead`. That session is now the fleet's lead. It plans
   with the human in its own chat.
3. The lead has the goal from that conversation. A lead Foil launched
   with `foil seat spawn lead --task "<goal>"` receives it as mail.
   Either one plans the work.
4. The lead spawns workers by role (`foil seat spawn implementer`) and
   kills them when they're done. Implementation seats get their own git
   worktree and branch.
5. Seats send short messages with `foil send`, share a thread with
   `foil post`, and put durable work products (task briefs, results,
   reviews, status) on the board.
   Send is one seat. Post is a room's members.
   A post wakes the room's members and the seats it names as `@name`, except a member whose last file there is a decline.
   The lead opens a room for a question that needs open discussion, names its members, changes them as the discussion moves, and closes it for a fresh one when the topic shifts or its history gets long.
   A worker replies in a room and does not open one.
   A room has a purpose, its first post, and members, and it is open or closed.
   A decline writes a file and wakes nobody.
   Status still comes from `status.md`.
   `foil send` one seat when the point is for that seat alone: a question or a correction.
   `foil post` when more than one other seat needs the same point.
   `foil post` when other seats need the point, not the lead alone.
   A worker asks the lead to open a room or to bring in a seat.
   The task file is the brief, and the mail is the pointer to it.
   The result file is the report. The mail is the pointer.
   A note wakes nobody.
   A note under `board/notes/` is scratch that wakes nobody.
   Do not put the result or a decision there.
   Do not continue a thread by mailing another seat.
6. Nobody polls. A joined lead ends its turn with `foil mail wait`
   running in the background. That command returns when mail or a room
   post for the lead arrives, or a seat dies, and can run a wake command
   for a harness that does not resume on its own. Every other `foil`
   command it runs prints one line when something is unseen (F41). It
   asks the human in its own chat. A launched seat is woken by its
   runner, which starts its next turn when mail or a room post for it
   arrives (F43). A launched lead asks through `status.md` and its mail
   to `user`.
7. The lead integrates the workers' branches, has the result reviewed,
   and reports completion in its status file. A launched lead integrates
   on its own goal branch, so several goals can run at once as several
   fleets on one checkout (F45).
8. After a crash or reboot, `foil seat resume` restarts dead seats. A
   seat near a full context writes `board/handoffs/<name>.md`, and
   `foil seat renew <name>` continues it in a fresh session with the
   same name, worktree, and branch (F44).
9. When the work is done, a joined lead writes `board/handoffs/lead.md`
   and runs `foil seat leave`. Mail to the lead queues. A later join, or
   `foil seat spawn lead` for a lead that runs while nobody is in the
   conversation, starts from that handoff (F42).

### Onboarding

Onboarding adds no command or flag beyond section 6. A coding agent
performs it, and becomes the lead by joining. The human's part is one
sentence; everything after step 2 is the agent's work.

1. Prerequisites are Python, Git, tmux, and at least one harness CLI that is already logged in. Foil never handles that login. The agent runs `foil` outside its own harness sandbox and without an approval prompt, a one-time setting per harness, because the store is outside the repository and a seat needs tmux and the network (F42). The same setting lets the agent's own file tools write the fleet's board, `<project folder>/fleets/<fleet>/board` in the store, and no other folder there. By hand it writes `board/status.md`, `board/tasks/<id>.md`, notes under `board/notes/`, and `board/handoffs/lead.md`, all on the board; mail, rooms, and memory go through `foil` commands. A persona edit the human asks for is outside the board, so the harness asks the human before that write, or refuses it. The harness, role, and mapping files, the personas, and the fleet's `run/` sit above the board, outside what its file tools may write. The `foil` check at join does not cover that, so the agent writes `board/status.md` once with its file tool before its first spawn. The setting does not cover `tmux`: an allowed `tmux` would let any session of that harness type any command into a tmux window, and no step needs it. The `foil` rule grants every `foil` command. `foil mail wait --wake` runs only a wake argv from the global layer or the package, never one the caller names (F41); a spawn still runs a project harness file's launch command (section 11). Before the first spawn, the agent runs `foil roster list`, names each distinct harness id the roster uses, and asks the human to run each of those once and accept its update, first-run, and opt-in dialogs, or to confirm that is done. The agent asks again when a role moves to a harness id that was not on that list. A launched seat runs its harness headless, one process per turn, so it has no dialog to answer: a turn that cannot go on without a person ends, and the seat reports what it needed (F43). An error seen in `foil seat peek` is reported to the human. Seats run as the same user and inherit the login (F26).
2. In the repository, the human asks the coding agent they already use: `Install Foil from https://github.com/TiantianFlow/foil, onboard this repository with it, and start a fleet. My goal: <goal>.`
3. The agent installs or updates Foil with `uv tool install --upgrade foil-ai`. Running it again updates an existing install. It checks that `foil --version` prints the version it expects, then runs `foil init` in the repository. The first init with no eligible harness installed exits `foil: no harness installed` and writes no project folder. The agent stops and does not spawn. The human installs a harness CLI and the agent runs `foil init` again. A global user preset whose command is on PATH counts as installed, including before a project folder exists (F27). When a harness is installed, `init` writes the project folder in the store and the missing global default roles, and reports what it found and what it wrote. The first line is the version. The report names every installed eligible harness (F27), the id each default role was given and why and whether that global row was written or left alone, `Available personas (use 'foil roster add')` when a packaged persona has no global role, one `Removed: <path>` line for each deleted project settings path, a built-in preset overridden by a global harness file, the permission choice, the project folder path, the star line when one is due (F34), and the pointer line. That report is the first thing the agent reads; the join brief in step 4 is the second.
4. The agent runs `foil seat join lead`, the pointer line's instruction: `Run foil seat join lead, then read the file it names. My goal: <goal>.` The brief names the lead's instruction file, which carries the lead skill in its joined form and the joined skill without Setup, Roster, The viewer, and Teardown and upgrading (F24, F42). Nothing is installed in the harness.
5. Before spawning any seat, the agent sets each template's harness list and permission, and adds any candidate role the goal needs with `foil roster add` beside a persona the lookup already resolves (F20, F22). A list of one entry is what `init` writes. `roster update ROLE harness=ID/MODEL,ID/MODEL` sets a list of any length in one value, in the form `roster list` prints, and `model` edits the entry of a one-entry list (F21). Each spawn of a role takes the next entry of its list, and an edited list starts at its first entry (F3). An omitted permission is `auto`: `permission = "auto"` is the default, and it asks the harness to skip approval prompts, though some harnesses still ask for some commands. `permission = "ask"` is the explicit choice, set by a caller outside the fleet: that seat's harness refuses an action that needs approval, and the seat reports what it needed instead. Each template carries its own permission. The agent pairs `auto` with a worktree when that seat can commit.
6. Foil launches each seat and delivers instructions with no harness-specific flags. The first turn's prompt inlines the instruction file, the role skill, persona, commands, and board conventions, when it is under 64 KiB, and otherwise names it (F24). That text tells the seat to re-read the instruction file whenever it is woken. When the lead spawns a worker, `--task` is the text of the first mail: the lead passes the task file's path, and Foil does not write the task file. A launched lead gets only the goal in `--task`. The role instructions arrive in the first prompt. The instruction file stays the single source. Harness system-prompt flags are not used.
7. The joined lead commits or sets aside its own work in progress before its first spawn, because a worker's worktree branches from the checkout's `HEAD`. After each spawn it waits for that seat's first mail or board file. Foil mails it from `foil` when that seat dies, pauses after failed turns, or ends a turn without a report (F41, F43). It then runs `foil seat peek` on that seat and reports an error to the human. It types nothing into a pane.
8. The joined lead does no project work itself. When the goal is done, it tells the human in its chat, writes the handoff, and leaves (F42).
9. Foil is one command for every project on the machine. Updating it changes the command under every live seat at once, but each seat keeps the instructions it was started with. A mid-goal upgrade works while the registry schema, the session-name derivation, and the `@foil-fleet-id` and `@foil-seat-id` markers stay compatible, and only when the project already lives in the store. An in-repo `.foil/` left by 0.3.x is not that case. The order is kill, then upgrade, then `foil init`: with the old `foil` still on `PATH`, `foil seat kill --all` in that project (a stale seat whose tmux window is already gone also counts), then upgrade, then `foil init`. A refused init creates nothing in the store. A 0.4.x command that still finds that directory does not say `foil: not initialized` (N8). When seats remain, it names them and this order. When none remain, it says to run `foil init`. The same order, with the installed `foil`, is how a later upgrade runs between goals: `foil seat kill --all`, `foil seat leave` for a joined lead, update, `foil init`, then `foil seat join lead`. The 0.5 series uses that order and is not a mid-goal upgrade. Neither is 0.7.0: its runner, plans, and presets differ from 0.6.x. `foil init` moves a project-root `board/` and `run/` under `fleets/main/` when the fleet copies are absent or empty. It deletes a project `templates/` without reading it, including `templates/<role>.toml`, and it does not leave those files to copy into `roles.toml` and `mapping.toml`.

## 4. Functional requirements

### Fleet and seats

| ID | Requirement |
|---|---|
| F1 | The command set is exactly the one in section 6. |
| F2 | The template named `lead` defines a launched lead, and the lead seat is always named `lead`, launched or joined (F42). A fleet has at most one live lead, and its first seat must be the lead. A new lead may be spawned or joined only after the previous one was killed or left. |
| F3 | `seat spawn` takes a template name, not a harness command. The role's mapping rows are one ordered list of harness entries (section 7.2). Spawn selects `entries[n % len(entries)]`, where `n` counts that role's successful spawns in this fleet since its lists last changed. The registry stores, per role, that count and the lists it counts for: the role's pair list and that fleet's override rows for the role, written as `roster list` prints them (section 7.5). A spawn whose lists differ from the stored ones starts at `n = 0`, so an edited list starts at its first entry. A killed or archived seat was a spawn, so it still counts. Every spawn of the lead, including one that replaces a killed lead, is a spawn, so each new lead takes the next entry. A renew counts as a spawn of that seat's role (F44). Resume is not a spawn and does not change `n`. A list of one stays on that entry; the length is not a special case. The chosen id and model are written on the new seat. When the chosen model is not one of that harness's `models` and that list is not empty, spawn prints one line on stderr, `foil: warning: model '<model>' is not in the models of harness '<id>': <ids>`, and launches anyway. When the fleet's overrides have rows for that role, those rows replace the role's mapping rows for that fleet, and spawn selects `rows[n % len(rows)]` with the same `n`. A row with a `harness` launches that id with the row's model, or with no model when the row has none. A row with only a `model`, the older form, makes `seat spawn` refuse when the pair list that row replaces has more than one entry. The refusal is one line, it names `foil roster update ROLE harness=ID/MODEL,ID/MODEL`, and it writes no seat record. When that pair list has one entry, the older row stays valid: it keeps the id that list selects and replaces only its model. A failed launch stores nothing, so a retry selects the same entry. Worker names are auto-numbered from the template name (`implementer-1`, `implementer-2`) unless `--name` is given. `--name user` is refused, because `user` is the human's mailbox (F14). A worker name is never reused while its record exists. After `seat archive` the name may be spawned again, and auto-numbering may reclaim it. |
| F4 | Only the lead or a caller outside the fleet may spawn, kill, archive, resume, or renew seats, or review memory (section 6.2). A joined lead is a caller outside the fleet and keeps that authority, including `permission` and roles. |
| F5 | A seat's identity comes from an environment variable Foil sets when launching it. A seat can't claim another identity through any flag. This protects against mistakes by cooperating agents, not against hostile processes, and the documentation says so. |
| F6 | When a template asks for a worktree, spawning creates a git worktree on a new branch whose name is unique in the repository. Killing a seat never deletes its branch and never silently destroys uncommitted work. `seat archive` does not delete a branch and does not delete uncommitted work. |
| F7 | Foil writes nothing into the working tree. It creates no exclude entry. Files and worktrees it creates never appear as untracked or modified files in the user's repository. |
| F8 | A launched seat whose exact tmux window exists and whose runner is still running is alive, and its state is `working` while a turn runs, `paused` after failed turns (F43), and `idle` otherwise. The other states are `dead` (the window is gone, or the runner has exited, and the seat wasn't killed), `killed` (stopped with `foil seat kill`, or a joined lead that left), and `joined` (the lead seat `foil seat join lead` wrote, with no window; no tmux fact is read for it). Whether the runner has exited is tmux's `#{pane_dead}` fact, not a reading of the pane. Which alive state a seat is in comes from its runner's record (section 7.5), and a record that is missing or unreadable reads as `idle`. A seat window stays after its runner exits, so the pane can still be read. |
| F9 | `seat resume` restarts `dead` seats and resumes `paused` ones, never `killed` or `joined` ones; without NAME it does both for every seat. A paused seat's resume writes `run/turns/<seat>.resume`, and its runner retries at once (F43). A dead seat's resume launches a new runner with the harness and model recorded on the seat at its last launch, and with that harness's preset. It does not read the template's list to choose again, it does not apply fleet memory, and it does not overwrite the seat's harness or model. When the runner record says the session exists (`started`) and its session id still matches the seat's registry session id (or the registry has none, as with an `output` preset), the first turn is the preset's `turn` argv on that session; otherwise it is `start`. For a `generated` preset that start uses the registry session when the runner record already carries that same unused id (F44), or when the registry session differs from the runner's; otherwise it uses a fresh id. A renew that is not yet adopted forces `start` even when the runner record still names an older started session, including an `output` preset's learned id (F44). Either way the first prompt says `You were restarted. Check before you repeat a merge, push, post or send.`, and the items that were in flight when the runner stopped are delivered again. A seat with no worktree resumes where F45 runs it. A seat that cannot be restarted is named in the error and does not stop the others. A killed name stays reserved until `seat archive`. A name that has been removed from `seats` is unknown, not killed. |
| F43 | A launched seat's tmux window runs Foil's runner, `python -P -m foil.runner PLAN`, which runs that seat's turns one at a time from `run/plans/<seat>.json`. The first turn runs the preset's `start` argv with the first prompt (F24). Every later turn runs its `turn` argv with the seat's session id and a wake prompt. A turn's stdin is `/dev/null`, its stdout and stderr reach the pane as written, and Foil keeps no copy of them (N5). The runner adds one line before each turn, `foil: turn started (start)` or `(turn)`, and one after it, `foil: turn ended (exit <code>)`. Between turns the runner checks about once a second for new items: mail in the seat's mailbox and `room/v2` files whose `wakes` names the seat, by the rules F41 uses for a mailbox, that are not in the delivered set. After the first new item it waits 1 second more for others, marks them all in flight, and starts the next turn. When deciding what is new, Foil reads at most the first 8 KiB of each candidate to parse front matter; a file whose front matter does not close in that window is skipped. The wake prompt lists each item as `time from path`, oldest first, up to 50 items, and then `...and N more: run foil mail list, and foil board list 'room/*/*.md' for posts.`; it inlines the body of each listed mail item of 600 bytes or less while the inlined bodies stay within 16 KiB, reading at most 601 body bytes to decide, and ends with the line to re-read the instruction file and to read the items not inlined with `foil mail read` or `foil board read`. When a turn exits, the runner records its end and exit code, and then ends any process left in the turn's process group. Each turn runs in its own process group, recorded in the runner's record, and one turn runs at a time. A turn that exits 0 delivers its items. Delivery is at least once: a runner that stops in a turn delivers that turn's items again when it starts next. A turn whose argv cannot be run, such as a missing program, ends with exit 127. A turn that exits non-zero runs again, with the same items and any new ones, after 30 seconds, 2 minutes, and 8 minutes. The session exists once a turn exits 0 or an `output` preset's id is learned, and the record marks it `started`; the runner writes that id and `started` to the record as soon as it learns the id, before the turn ends. Until the session is started, a failed `start` runs `start` again, on a fresh id for a `generated` preset, and after that a retry runs `turn`. When the third retry fails, the seat is `paused`, and Foil mails the lead from `foil`, or `user` when the seat is the lead: `<seat> paused after 4 failed turns (exit <code>). See foil seat peek <seat> --lines 200. foil seat resume <seat> retries.` A paused runner starts no turn until `run/turns/<seat>.resume` appears, then removes that file and runs the batch with any new items. A turn that runs past its role's `turn_timeout` (section 7.2) is ended with its process group. When the session is already started, that turn is not retried and its items are delivered. When it is not, the items stay in flight and the next turn is `start` again, on a fresh id for a `generated` preset. Either way Foil mails the same reader `<seat>'s turn passed turn_timeout and was stopped. See foil seat peek <seat> --lines 200.` When a worker's turn exits 0 and no mail from that seat, no room file from it, and no file under `board/results/` was written during the turn, Foil mails the lead `<seat> ended a turn without mail, a post, or a result. See foil seat peek <seat> --lines 200.` A spawn and a renew seed the delivered set with every item already present before the runner starts, so mail from an earlier goal is not new. The task mail is in flight for the first turn instead, so the first prompt lists it and a runner that stops in that turn delivers it again. After that only the runner writes its record. The runner never sets an identity: `FOIL_SEAT_ID` and the rest of the environment come from the plan (F5). When its window is closed, the runner ends the running turn's process group and exits. |
| F44 | `foil seat renew NAME` gives a seat a fresh session and keeps its name, worktree, branch, and mailbox. It needs `board/handoffs/<name>.md`, with no symlink at `board/`, `board/handoffs/`, or the file, and otherwise prints `foil: write board/handoffs/<name>.md first`. Under the registry lock it re-reads the seat, refuses it when it is now killed, joined, or its window or session id changed, takes the role's next harness entry (F3), and records the new harness, model, and session id on the seat in that same write. It then marks the renew pending, resets that seat's runner record to the new session with `started` false, keeping the prior delivered set and adding every item present at the renew, so a crash before `.renew`—or a runner write that restores the old record—cannot resume the new harness on the old session. Kill, archive, and spawn clear that pending mark for the seat name. Then it writes a new instruction file whose first-launch line says to read that handoff first, and a new plan. An alive seat then gets `run/turns/<name>.renew` so its runner starts the new session after its current turn, or at once when no turn runs. A dead seat is launched again with the new plan. Either way the delivered set keeps what it had and adds every item present at the renew, and the first prompt is the new instruction file. A launched lead may renew any seat, itself included. A caller outside the fleet, a joined lead included, may renew any launched seat. A worker gets `foil: not allowed`. `seat renew lead` on a joined lead prints `foil: lead is joined. It has no pane.`, and a killed seat gets `foil: seat '<name>' is killed`. |
| F45 | Several goals run at once as several fleets on one checkout (`FOIL_FLEET`, F20). A launched lead gets a worktree on a new branch `foil/goal-<fleet>`, made unique as F6 makes a branch name, from the checkout's `HEAD`, and integrates there. In that fleet a worker's worktree branches from the lead's branch, and a seat whose role has no worktree runs in the lead's worktree. Under a joined lead, or with no lead worktree, workers branch from the checkout's `HEAD` and a seat without a worktree runs in the project checkout. `seat spawn lead` run outside the fleet ends with a note under 1 KB for whoever supervises that lead: the fleet, the lead's branch and worktree, `foil mail wait --all-fleets` to hear its mail to `user`, `FOIL_FLEET=<fleet> foil send lead TEXT` to answer, the `status.md` path, and to merge the branch once `status.md` says done. `seat list --all-fleets` and `mail wait --all-fleets` read every fleet of the project (section 6.1). |
| F42 | `foil seat join lead` runs outside the fleet only and needs an initialized project. It first checks that it can write the fleet's `run/` folder and start tmux; when either fails it prints `foil: run foil outside your harness sandbox and without a prompt` and changes nothing. It refuses with `foil: lead is <state>. Run foil seat kill lead first`, naming `alive` or `dead`, when the lead seat is stored in a state other than `killed` or `joined`, and with `foil: lead is joined. Pass --take to take it` when it is `joined` and `--take` is not given. It writes the `lead` seat as `joined`, with no window, worktree, or branch. Its harness is `--harness ID`, or `codex`, `claude`, or `grok` when `CODEX_THREAD_ID`, `CLAUDE_CODE_SESSION_ID`, or `GROK_SESSION_ID` is set, checked in that order, or empty; its session id is `--session ID`, or else the value of the variable for the harness in use, so a `--harness` that names another harness than the detected one records no session id. Both must be safe ids. The session id is shown in the brief and in `seat list`, not checked: it is not a lock (F5). The brief names `foil mail wait --wake` as the route when the harness preset has a `wake` and the session id it needs was recorded; otherwise it names a background `foil mail wait` for `claude` and `grok`, and the turn-start check for the rest. A join is not a spawn and does not change the rotation (F3). A join that fails leaves the lead seat as it was: the refusals come before any write, the instruction file is written before the seat, and a failure after the seat is written puts the previous lead record back. ## 7. Data design

### 7.1 Layout

Everything for one project lives in one folder in a per-user store (F7).
The store root is `$FOIL_HOME` when that is set, made absolute so a
relative value does not follow a later working directory, otherwise
`$XDG_DATA_HOME/foil`, otherwise `~/.local/share/foil`. The project
folder is `<root>/projects/<key>/`. `<key>` is a readable slug of the
realpath of the Git common dir plus a short hash. The main checkout, a
linked worktree, and a seat worktree share that common dir, so they
share one folder. `project.json` records the main checkout, the origin
remote when there is one, without HTTP userinfo, the root commit when there is exactly one, and
the creation time. Init keeps a recorded
path that still exists. Otherwise it records the parent of the Git
common dir, including when init runs from a linked or seat worktree. After adopt or a
legacy move, and only after `git worktree repair` succeeds, absolute paths in `run/registry.json`, `run/plans/`, `run/instructions/`, and
`run/archive/` are rewritten to the store paths no matter
what the old absolute prefix was, including a repository directory that
was renamed, and whether or not any seat has a worktree. The old prefix covers the old checkout, the old `.foil/` directory, and each seat worktree. The old `.foil/` prefix is read from a worktree's gitdir text before repair. The rewrite also matches a path that JSON stored with escapes. A stale
`FOIL_PROJECT` value stored in `run/plans/*.json` is rewritten to the
current project key, and that write is atomic (N7). A failed repair leaves the stored paths unchanged. A later init maps the old store root or the old `.foil/` whenever that directory itself no longer exists. When the gitdir no longer names that store, the old folder is `<projects>/` plus the project key of the checkout recorded before the write. The check that its parent is gone applies only when rewriting the old checkout to the current one. The recorded checkout used for that retry is the path saved before this run writes the current checkout. A recorded checkout that no longer
exists is rewritten to the main checkout. A seat's environment
includes `FOIL_PROJECT` set to that key. It also includes `FOIL_HOME`
or `XDG_DATA_HOME` when the spawning process had that variable set, so
the seat resolves the same store. Every command resolves the project
the same way. `FOIL_PROJECT`, when it names a folder that has
`project.json`, selects that folder's recorded repository path.
Otherwise the command uses the Git toplevel of the working directory,
then the same key. The main checkout, a linked worktree, and a seat
worktree share the Git common dir, so they share the folder.
Global settings live at the store root. A project file is an optional
override. `<root>/star.json` stays one record for the store (F34). The concepts below
are fixed; exact names may vary.

```text
<root>/
  roles.toml                   the roles. init writes each missing default
  mapping.toml                 each role's pair list. init writes missing rows
  harnesses.toml               only harnesses someone changed
  harnesses/<id>.toml          one harness; beats the global list entry
  personas/<role>.md           only personas someone changed
  projects/<key>/
    project.json               path, origin, root, created
    roles.toml                 optional whole-role overrides
    mapping.toml               optional whole-list overrides
    harnesses.toml             optional
    harnesses/<id>.toml        optional
    personas/<role>.md         optional
    fleets/<id>/               one fleet. FOIL_FLEET, default main
      overrides.toml           optional pair list for that fleet
      board/
        mail/<seat>/<time>-<from>-<rand>.md
                               mail/user/ is the human's mailbox (F14)
        notes/                 unaddressed shared files
        room/<id>/<id>.md      room/v2 thread, and children beside it
        status.md              lead's status (status/v1)
        tasks/<id>.md          task/v1
        results/<id>.md        result/v1
        handoffs/<name>.md     a seat's handoff (F42, F44)
      run/                     registry, archive, plans, instructions
        plans/<seat>.json      what the seat's runner runs (F43)
        turns/<seat>.json      the runner's record (F43)
        turns/<seat>.resume    a resume request for a paused seat (F9)
        turns/<seat>.renew     a renew request for an alive seat (F44)
        foil/<mailbox>/<name>  Foil's record of its own mail (F14)
        seats/<name>.json      what mail wait has shown that mailbox (F41)
        archive/<time>-<name>.txt
                               archived seat, prose, not in the registry
    memory/                    project lessons; survive fleets
    skills/                    directory stays. init writes no skill.
                               Every skill is read from the package.
    worktrees/<label>          one directory per seat worktree
    hooks/                     pre-commit and pre-push for seats (F40)
```

### 7.2 Template

`roles.toml` is the profile list. `mapping.toml` is the default harness and model list: one or more `[[map]]` rows per role, in spawn order (F3). `init` writes one global row per missing default role and omits `model`. Spawn reads that list (F3). There is no second harness string or model field beside it. Permission defaults to `auto`.

```toml
# roles.toml
[[role]]
id = "implementer"
description = "Implements the task on its own branch."
persona = "personas/implementer.md"
worktree = true
permission = "auto"

# mapping.toml
[[map]]
role = "implementer"
harness = "claude"

[[map]]
role = "implementer"
harness = "codex"
model = "gpt-6.1-sol"
```

A profile is one `[[role]]` row. Each mapping row is one `[[map]]` with `role`, `harness`, and an optional `model`. `roster add --from FILE` reads one document with `persona`, `worktree`, `permission`, and `[[harness]]` entries, and writes those into the two lists. That document is not stored.

| Field | Required | Meaning |
|---|---|---|
| `harness` | yes | Ordered `[[map]]` rows for that role. Each row has `role`, `harness` (a preset id, and a safe id), and optional `model` (passed to that preset's model option). An empty list, a row that is not a table, a missing or empty harness id, or a key other than `role`, `harness`, and `model` is invalid. |
| `persona` | no | Inline text, or a path to a Markdown file. |
| `worktree` | no, default `false` | Give each seat its own worktree and branch. |
| `permission` | no, default `auto` | `ask` or `auto`, mapped to the preset's flags. |
| `turn_timeout` | no, default `14400` | Seconds one turn of this role may run before the runner ends it (F43). A whole number from 1. Set in `roles.toml`; `roster update` does not edit it. |

A role with one CLI is a list of one. `init` and `roster add` without `--from` write one entry and omit `model` when there is none. `model` omitted on an entry is empty.

### 7.3 Harness preset

| Field | Meaning |
|---|---|
| `id` | Preset name. |
| `start` | Argv for a seat's first turn. Placeholders: `{model}`, `{prompt}`, `{session_id}`, `{permission}`. Each is a whole argument, and `{prompt}` is required. |
| `turn` | Argv for every later turn, on the same session. The same placeholders, and `{session_id}` is required. |
| `permission.ask`, `permission.auto` | Extra argv for each mode, added to `start` and `turn` at `{permission}`, or at the end without it. `{permission}` comes before every other placeholder, so a CLI subcommand that takes the prompt last can still take the flags. `auto` asks the harness to run without approval prompts. `ask` adds nothing, so a headless turn refuses an action that needs approval. |
| `wake` | Optional argv that wakes a joined lead's session from outside it, using `{session_id}` and `{text}` (F41). Each placeholder is a whole argument. It runs without a shell, and only from the global layer or the package. |
| `session_id` | `generated` (Foil creates a UUID and passes it to every turn) or `output` (the CLI makes the id, and the runner reads it from the first turn's stdout, F12). |
| `session_key` | With `output`, the key of the session id in the CLI's JSON output line, such as `thread_id`. Required with `output` and refused otherwise. |
| `env` | Names of further environment variables to forward. A named variable takes its value from the tmux server's environment. `PATH` comes from the spawning caller. `PATH` and `HOME` are always forwarded (F26). |
| `set_env` | Optional table of fixed `NAME = "value"` rows set for every launch, such as a harness's own setting. Not for secrets: the value is stored in the plan. A name the preset also forwards, `PATH`, `HOME`, `XDG_DATA_HOME`, and names that start with `FOIL_` or `GIT_` are refused (F26). |
| `unverified` | Names of the parts of this preset that have not been run live against the CLI. |
| `models` | Ids this harness accepts. Spawn and `roster` warn about a model that is absent, and do not reject it. An empty list names none and warns about nothing. |

A preset with `command` or `resume`, the keys before 0.7.0, does not load: the error is one line, `foil: <file>: command and resume are now start and turn`, naming the harness file or list it came from.

Built-in presets use each CLI's documented headless flags, with the
prompt placed right after the flag that takes it, because a variadic
flag such as `claude --disallowedTools` would take a prompt that
follows it. A flag that could not be verified live is named in
`unverified`.

| Harness | `start` | `turn` | `session_id` | `auto` |
|---|---|---|---|---|
| `claude` | `claude -p PROMPT --session-id ID` | `claude -p PROMPT --resume ID` | `generated` | `--permission-mode auto` |
| `codex` | `codex exec --json PROMPT` | `codex exec --json resume ID PROMPT` | `output`, `thread_id` | `--dangerously-bypass-approvals-and-sandbox` |
| `gemini` | `gemini -p PROMPT --session-id ID --skip-trust` | `gemini -p PROMPT --resume ID --skip-trust` | `generated` | `--approval-mode yolo` |
| `opencode` | `opencode run --format json PROMPT` | `opencode run --format json --session ID PROMPT` | `output`, `sessionID` | `--auto` |
| `grok` | `grok -p PROMPT --session-id ID` | `grok -p PROMPT --resume ID` | `generated` | `--always-approve` |

Each also passes `--model MODEL` when the entry names a model. A seat writes the fleet's board and the project's Git common dir, both outside its worktree, so a sandbox that allows writes only in the worktree would refuse its `foil` commands and commits; `codex` `auto` therefore turns its sandbox off, as the other harnesses' `auto` flags skip their prompts.

### 7.4 Board files

**Mail:** Markdown with front matter `contract: mail/v1`, `from`, `to`,
`time` (UTC, ISO 8601), and an optional `re` (the mail file it answers),
followed by the body. Written atomically; file names never collide.
`foil send` does not write `re`.

**Room:** Markdown with front matter `contract: room/v2`, `from`, `time`
(UTC, ISO 8601), an optional `re` (the room file it answers), and `wakes`
(the seat ids the post wakes, sorted). A room's first file, and a post that
changes its members, add `members` (seat ids, sorted). A close adds
`closed: true`. There is no `generation` field. A waking file's body
starts with a short preamble, then the caller's text, and a close's body
starts with `This room is closed. Foil refuses a reply here.` A decline's
body is the line `decline` and its `wakes` list is empty. Written
atomically; file names never collide. A reply reads `contract`, `from`,
`time`, `members`, `closed`, and the body of each `room/v1` or `room/v2`
file in its room to find the members to wake (F33). A `room/v1` file
from an earlier release still counts for the room's state and wakes
nobody.

**Contracts:**

| Contract | Front matter |
|---|---|
| `status/v1` | `state: working \| blocked \| done`, `updated`, `questions` (list, may be empty), `decisions` (list, may be empty: one line per decision the lead made, `<choice>. Evidence: <evidence>. Undo: <how>.`) |
| `task/v1` | `id`, `owner`, `state: open \| doing \| done`, `acceptance`, optional `source` (where the task came from: the goal, a result, or a question) |
| `result/v1` | `task`, `author`, `branch` (if any), `outcome: pass \| fail \| blocked \| dropped`, optional `question` (what a `blocked` result needs answered) |

**Mandate.** The `status/v1` body starts with `## Mandate`: `May decide:`,
`Must stop for:`, and `Done when:`, one line each, from the goal and the
human's answers. The lead reads it before it asks or decides (section 8).

**Checklist.** Once the lead has a plan, the `status/v1` body holds a
`## Checklist` of Markdown task items, one per line: `- [ ]` open,
`- [x]` done. An item starts with its task id when it has one.
`state: done` means every item is ticked. The front matter is unchanged.
Foil parses front matter only to print a file and does not act on contract fields (F16).

### 7.5 Foil-owned state

**Memory lesson** (schema-versioned): id, text, proposer, time, state
(`proposed`, `accepted`, `rejected`, `superseded`), reviewer, and an
optional `replaces`.

**Fleet overrides** (`fleets/<id>/overrides.toml`): zero or more `[[override]]` rows with `role`, an optional `harness`, a `model` that may be omitted only when `harness` is set, and an optional `note`. A role's rows, in order, are that fleet's list for the role, and spawn selects from it as it does from the mapping (F3). The workspace is the path in `project.json`. Posts are files under that fleet's `board/room/`. A caller inside the fleet writes rows with `roster update ROLE harness=ID/MODEL,ID/MODEL` or `model=VALUE`, and those rows always name a harness. A caller outside the fleet edits the global mapping, unless `--project`, which writes that role's whole project list. The lead instruction names the overrides file and says to re-read it before spawn. Spawn applies the selected row's model as the harness model flag. Resume does not read fleet memory (F9).

**Star record** (schema-versioned JSON, `<root>/star.json`, one per store): `shown`, the days a star line was printed; `minor`, the `X.Y` version at the last line; and `stop`, which the agent that ran `init` sets when the human declines (section 8, F34).

**Runner record** (schema-versioned JSON, `fleets/<id>/run/turns/<seat>.json`, one per launched seat): `session_id`, the session the next turn uses; `delivered`, the board paths already given to a turn, relative to the board; when the record is saved, paths whose files no longer exist are dropped, and if the record would still exceed its size limit the oldest remaining paths are dropped too (delivery stays at least once); `inflight`, the paths the running or failed turn was given; `turn_started`, the start time of the running turn or `null`; `last_exit`, the exit code of the last turn that ended, `null` before one ends, and `-1` for a turn ended by `turn_timeout`; `failures`, the failed turns in a row; `started`, whether a turn on this session exited 0 or an `output` preset's id was learned; `paused`; and `pgid`, the running turn's process group or `0`. Spawn, resume, and renew write it before the runner starts (F43); after that only the runner writes it, atomically (N7). `foil seat kill` reads `pgid` to end a running turn. A missing file is an empty record.

**Plan** (`fleets/<id>/run/plans/<seat>.json`, written by spawn, resume, and renew): the `start` and `turn` argv with `{prompt}` and `{session_id}` left for the runner, which fills `{session_id}` from its record or, before that has one, from the plan's `session_id`; `session_key`; `cwd`; `env` and `env_forward` (F26); the instruction file; `reader`, the mailbox Foil's pause and timeout mail goes to; `worker`, whether the silent-turn check applies; `turn_timeout`; the retry waits; and `first`, whether the first turn is `start` or `turn`. A plan from 0.6.x does not load, and the runner prints one line.

**Seen record** (schema-versioned JSON, `fleets/<id>/run/seats/<name>.json`, one per mailbox a caller outside the fleet reads, `lead` or `user`): `seen`, the board paths already shown, relative to the board; `quiet`, the quiet waits in a row (F41); `reported`, the seats reported dead and not seen alive since; `checked`, the time of the last dead-seat check; and, for `lead`, `joined`, the time of the join. A missing file is an empty record. Only `seat join`, `mail wait`, and the new-items line write it, atomically (N7).

**Registry** (schema-versioned JSON): fleet id, tmux session, lead name,
and per seat: name, template, harness, model, tmux window id, state, worktree
path, branch, and session id (a joined lead stores `joined`, no window, and the harness and session `seat join` found), and per role a `rotation` record: `list`, the lists the last spawn of that role selected from, and `next`, the count the next spawn uses when those lists are unchanged (F3). A record written without `rotation` loads it as empty. `harness` and `model` on a seat are the pair recorded at that seat's last launch. Resume keeps them (F9). ## 10. Verification

Principle: **real Foil, real tmux, real git, a small real task; only the
agent is replaced.** Tests check real outcomes (tests pass, a branch
exists, a window is gone), not Foil's reports about itself.

**Fake harness** (the `fake` preset) is a test double for a headless agent CLI:

- It runs one turn and exits, like a real CLI in headless mode. `start` and `turn` both name the session id, and a turn whose session id differs from the one its seat's first turn got exits 9.
- It reads the files the prompt names, mail or room files, and the task mail the first prompt names.
- It follows a per-seat script, in a format the standard library can
  parse. Reactions include running a shell command (for example
  `foil seat spawn`, `git commit`, the fixture's test runner), writing a
  board file, and `foil send`.
- A script can make a turn fail: exit with a code, wait, hang until it is ended, leave a child process running, or end without any report.
- It records each turn's argv, prompt, stdin, and working directory, which the scenarios check. It also keeps a debug log; tests never assert on it.
- Each seat finds `foil` and `python3` on `PATH` as shims for the interpreter that runs the tests, so a seat runs the Foil under test and not another install, with the test interpreter's directory off `PATH`.
- It launches through the normal preset path, so templates, launch,
  environment, instruction files, worktrees, and turns are exercised
  exactly as with a real CLI.

**Stand-ins** for the built-in presets are small programs named `claude`, `codex`, `gemini`, `opencode`, and `grok` that parse the flags their preset passes the way this document says that CLI takes them, refuse any other, and print a session line where the preset's `session_id` is `output`. They check Foil's argv and the session round trip. They do not check the real CLI.

**Outside agent:** a test double for the human's own agent that runs `foil mail wait` in the background, as the joined skill says, and acts on what it returns.

the test plays the human's agent):

## 11. Out of scope

- Any command, subcommand, or flag not in section 6. Changing the command
  surface requires changing this document first.
- Parsing or interpreting pane contents or a turn's output. The only exception is the session id an `output` preset prints, bounded by F12.
- Keeping a joined lead's file tools from changing what a spawn runs. Spawn and resume read a project harness file (F20, F27), so a joined lead whose file tools may write more than the fleet's board (onboarding step 1) could set a launch command that runs outside its sandbox. The board-only setting and the joined skill's rule against writing harness files are the guards. Only `--wake` reads no project harness file (F41).
- Remote machines and Windows. A project is one copy of the code. Several fleets may run on it. They share the effective roles, harnesses, and mapping. Each fleet has its own board, posts, registry, and an optional pair-list override. Seat worktrees stay in the same Git repository.
- A UI or server other than `foil view`; a viewer that writes, or types into a pane; a daemon mode, or a command that installs a service; MCP; or a hosted service.
- Message read receipts, usage-based dispatch, and persona catalog tools beyond `roster list` of the personas `init` copied. Usage-based dispatch includes quota detection, probes, pacing, credential rotation, and switching a running seat because it looks exhausted. Spawn-time rotation across the ordered harness list on a role is in scope. A spawn selects `entries[n % len(entries)]`, where `n` counts that role's spawns since its lists last changed (F3). That spreads later spawns, the lead's included, across the entries the role was given. It does not balance usage and it does not move a seat that is already running. Foil does not read or show a harness's token usage or quota.
- Context monitoring. Foil does not read a seat's context use. A seat near a full context, or at a milestone the lead picks, writes a handoff file, and the lead or a caller outside the fleet replaces it (section 8).
