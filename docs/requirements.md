# Foil requirements

## 1. Summary

Foil is a lightweight command-line tool for running a fleet of CLI coding
agents in tmux. A human works through their own agent harness, the
*operator*, which uses Foil to start a *lead* agent and hand it a goal.
The lead spawns worker agents from role templates, directs them, and
integrates their work. Agents talk through short messages and shared
files. Anyone can peek at an agent's screen, but Foil never interprets
what it shows. All project work is done by the fleet, never by the
operator.

## 2. Glossary

| Term | Meaning |
|---|---|
| Operator | The human's own harness, outside the fleet. It is never a seat. Foil sees it as "a caller outside the fleet". |
| Fleet | One running group of seats for a project. A project has one copy of the code. Several fleets may run at once. They share the effective roles, harnesses, and mapping: packaged, then global, then project. Each fleet has its own board, posts, registry, and an optional pair-list override. |
| Seat | One agent process in its own tmux window. |
| Lead | The one seat allowed to spawn and kill other seats. |
| Worker | Any seat that isn't the lead. |
| Template | A role profile: a description, a persona, a worktree flag, and a permission mode. The profiles are one list. The default harness and model for each role are a second list. Global is the settings. A project file is an optional whole-role or whole-list override. A fleet file is an optional pair list. |
| Harness preset | How to launch one agent CLI (for example `claude` or `codex`), including the model ids that CLI accepts. The presets are one list. |
| Board | A shared folder all seats can read and write, holding mail, room threads, notes, and contract files. |
| Mail | A message to one seat, stored as one file on the board. |
| Room | A thread of files under that fleet's `board/room/<id>/`. A waking `post` nudges every other alive seat in that fleet. |
| Nudge | The one line Foil types into a seat's pane to announce new mail or a room file. The line is the sender and an absolute path. |
| Note | An unaddressed shared file on the board (the notepad). |
| Contract | A board file with an agreed, versioned format. |
| Memory | Reviewed lessons for the project. They outlive fleets and are given to every new seat. Fleet memory is separate: it belongs to one fleet and can name the harness and model list to use for a role from the next spawn on. |
| Peek | Printing the raw last lines of a seat's pane. |

## 3. Workflow

```text
human ──▶ operator (outside the fleet)
             │  foil init · foil seat spawn lead · foil send lead
             │  foil seat list · foil seat peek lead
             ▼
        ┌──────────── tmux: one fleet ─────────────┐
        │  lead ──spawn/kill──▶ implementer-1       │
        │   │                   implementer-2       │
        │   └──send──▶          reviewer-1          │
        └───────────────────────────────────────────┘
             all seats read/write the board
```

1. The human asks the operator for something.
2. The operator runs `foil init` once per project, then
   `foil seat spawn lead --task "<goal>"`.
3. The lead receives the goal as mail and plans the work.
4. The lead spawns workers by role (`foil seat spawn implementer`) and
   kills them when they're done. Implementation seats get their own git
   worktree and branch.
5. Seats send short messages with `foil send`, share a thread with
   `foil post`, and put durable work products (task briefs, results,
   reviews, status) on the board.
   Send is one seat. Post is every other alive seat.
   `foil send lead` is the goal, the human's answer, and a nudge when the lead looks stuck.
   Ordinary human answers stay `foil send lead`.
   `foil post` is for words the human wants every alive seat to see, such as a question for the whole fleet.
   You are outside the fleet, so that post reaches every alive seat.
   A decline writes a file and types nothing.
   List `board/room`. If threads exist, tell the human that a room exists.
   Read a thread when the human asks about it, or before you post.
   Status still comes from `status.md`.
   Do not guess progress from a room file you have not read.
   `foil send` one seat when the point is for that seat alone: a question or a correction.
   `foil post` when more than one other seat needs the same point.
   `foil post` when other seats need the point, not the lead alone.
   The task file is the brief, and the mail is the pointer to it.
   The result file is the report. The mail is the pointer.
   A note wakes nobody.
   A note under `board/notes/` is scratch that wakes nobody.
   Do not put the result or a decision there.
   Do not continue a thread by mailing another seat.
6. Every few minutes the operator checks in: it lists seats, peeks at the
   lead, and reads the lead's status file. It passes the lead's questions
   to the human, sends the human's answers to the lead, and nudges the
   lead if it looks stuck. It does no project work. The lead doesn't know
   an operator exists; it acts as if a human is talking to it.
7. The lead integrates the workers' branches, has the result reviewed,
   and reports completion in its status file.
8. After a crash or reboot, `foil seat resume` restarts dead seats.

### Onboarding

Onboarding adds no command or flag. A coding agent performs it. The
human's part is one sentence; everything after step 2 is the agent's work.

1. Prerequisites are Python, Git, tmux, and at least one harness CLI that is already logged in. Foil never handles that login. Before the first spawn, the agent runs `foil roster list`, names each distinct harness id the roster uses, and asks the human to run each of those once in the repository root and accept its folder-trust, update, first-run, and opt-in dialogs, or to confirm that is done. Trust is per harness per path. A seat worktree lives in the store, outside the repository, so it does not inherit the repository's trust. Each seat label needs folder trust once per harness. The agent asks again when a role moves to a harness id that was not on that list. A seat waiting at one of those looks from outside exactly like a seat that is working. A dialog seen in `foil seat peek` is answered by the agent only when it is an approval dialog, as F12 bounds it. Every other dialog is reported to the human and not answered. Seats run as the same user and inherit the login (F26).
2. In the repository, the human asks the coding agent they already use: `Install Foil from https://github.com/TiantianFlow/foil, onboard this repository with it, and start a fleet. My goal: <goal>.`
3. The agent installs or updates Foil with `uv tool install --upgrade foil-ai`. Running it again updates an existing install. When it says `Executable already exists: foil`, an install from before the rename to `foil-ai` is in the way, and the agent runs `uv tool uninstall foil-orchestrator` and the install line again. It checks that `foil --version` prints the version it expects, then runs `foil init` in the repository. The first init with no eligible harness installed exits `foil: no harness installed` and writes no project folder. The agent stops and does not spawn. The human installs a harness CLI and the agent runs `foil init` again. A global user preset whose command is on PATH counts as installed, including before a project folder exists (F27). When a harness is installed, `init` writes the project folder in the store and the missing global default roles, and reports what it found and what it wrote. The first line is the version. The report names every installed eligible harness (F27), the id each default role was given and why and whether that global row was written or left alone, `Available personas (use 'foil roster add')` when a packaged persona has no global role, one `Removed: <path>` line for each deleted project settings path, `Skill: <root>/skills/operator.md` when that file exists and `Skill: packaged <package path>` otherwise, a built-in preset overridden by a global harness file, the permission choice, the project folder path, the star line when one is due (F34), and the pointer line. That report is the first thing the agent reads; the operator skill in step 4 is the second.
4. The agent reads the operator skill at the path the pointer line names and follows it. An agent that was started without the sentence in step 2 gets the same instruction from that line: `Read <root>/skills/operator.md and follow it. My goal: <goal>.` when `<root>/skills/operator.md` exists, and otherwise `Read <package path> and follow it. My goal: <goal>.` `<package path>` is the absolute path the `Skill:` line named. That needs nothing installed in the harness. A persistent install is optional: copy the skill where that harness discovers skills, at user level, so it stays out of `git status` (F7).

| Harness | Install path | Verified |
|---|---|---|
| any | the pointer line above | required; not a per-harness install |
| Claude Code | `~/.claude/skills/foil-operator/SKILL.md` | no |
| grok, codex, opencode, gemini | none published | no |

5. Before spawning any seat, the agent sets each template's harness list and permission, and adds any candidate role the goal needs with `foil roster add` beside a persona the lookup already resolves (F20, F22). A list of one entry is what `init` writes. `roster update ROLE harness=ID/MODEL,ID/MODEL` sets a list of any length in one value, in the form `roster list` prints, and `model` edits the entry of a one-entry list (F21). A spawn takes the entry at the count of seats already stored for that role (F3). An omitted permission is `auto`: `permission = "auto"` is the default, and it asks the harness to skip approval prompts, though some harnesses still ask for some commands. `permission = "ask"` is the explicit choice, set by a caller outside the fleet: that seat stops at its first approval prompt and waits for the human in that pane. Each template carries its own permission. The agent pairs `auto` with a worktree when that seat can commit.
6. Foil launches each seat and delivers instructions with no harness-specific flags. The first launch prompt inlines the instruction file: the role skill, persona, commands, and board conventions. That text tells the seat to re-read the instruction file whenever it is woken. The operator puts only the goal in `--task`. When the lead spawns a worker, `--task` is the text of the first mail: the lead passes the task file's path, and Foil does not write the task file. The role instructions arrive in the first prompt. The instruction file stays the single source. Harness system-prompt flags are not used.
7. The agent's first task is the first-run check: spawn the lead with `Write board/status.md with state: done`, then wait a few minutes. `seat spawn --task` writes that task as mail before launch and types nothing into the new pane, so a seat at a startup dialog waits there. If `board/status.md` is already there from an earlier goal, the agent notes its `updated` value before the spawn, and the check passes only when `updated` changes and the file shows `state: done`. If the file does not appear or `updated` does not change, the agent runs `foil seat peek lead`. It may send keystrokes only for an approval dialog, as F12 bounds it: a folder-trust prompt, a login prompt, or a prompt that blocks the seat until a human or the agent approves it. An update dialog, a first-run dialog, an opt-in, and an error are reported to the human and not answered. If that lead is dead, the agent runs `foil seat kill lead` and spawns the check again only after that seat is gone. It does not spawn a second lead while one exists. A seat with its own worktree may stop on folder trust for that worktree's path in the store. The same label asks once per harness.
8. When the check passes, the agent sends the goal to that lead and does no project work itself.
9. Foil is one command for every project on the machine. Updating it changes the command under every live seat at once, but each seat keeps the instructions it was started with. A mid-goal upgrade works while the registry schema, the session-name derivation, and the `@foil-fleet-id` and `@foil-seat-id` markers stay compatible, and only when the project already lives in the store. An in-repo `.foil/` left by 0.3.x is not that case. The order is kill, then upgrade, then `foil init`: with the old `foil` still on `PATH`, `foil seat kill --all` in that project (a stale seat whose tmux window is already gone also counts), then upgrade, then `foil init`. A refused init creates nothing in the store. A 0.4.x command that still finds that directory does not say `foil: not initialized` (N8). When seats remain, it names them and this order. When none remain, it says to run `foil init`. The same order, with the installed `foil`, is how a later upgrade runs between goals: `foil seat kill --all`, update, `foil init`, then spawn the lead with the first-run check (step 7). The 0.5 series uses that order and is not a mid-goal upgrade. `foil init` moves a project-root `board/` and `run/` under `fleets/main/` when the fleet copies are absent or empty. It deletes a project `templates/` without reading it, including `templates/<role>.toml`, and it does not leave those files to copy into `roles.toml` and `mapping.toml`. The earlier goal's `status.md` already says `state: done`, so the check waits for its `updated` value to change. Re-copy any user-level copy of the operator skill.

## 4. Functional requirements

### Fleet and seats

| ID | Requirement |
|---|---|
| F1 | The command set is exactly the one in section 6. |
| F2 | The template named `lead` defines the lead, and its seat is always named `lead`. A fleet has at most one live lead, and the first seat spawned must be the lead. A new lead may be spawned only after the previous one was killed. |
| F3 | `seat spawn` takes a template name, not a harness command. The role's mapping rows are one ordered list of harness entries (section 7.2). Spawn selects `entries[n % len(entries)]`, where `n` is the number of seat records already stored for that role, including killed seats, counted before the new seat is inserted. A list of one stays on that entry; the length is not a special case. The chosen id and model are written on the new seat. When the fleet's overrides have rows for that role, those rows replace the role's mapping rows for that fleet, and spawn selects `rows[n % len(rows)]` with the same `n`. A row with a `harness` launches that id with the row's model, or with no model when the row has none. A row with only a `model`, the older form, makes `seat spawn` refuse when the pair list that row replaces has more than one entry. The refusal is one line, it names `foil roster update ROLE harness=ID/MODEL,ID/MODEL`, and it writes no seat record. When that pair list has one entry, the older row stays valid: it keeps the id that list selects and replaces only its model. A failed launch writes no seat record, so a retry selects the same entry. The lead reuses the single registry record named `lead`, so the count is 0 before that record exists and 1 before every later launch, including one that replaces a killed lead. Worker names are auto-numbered from the template name (`implementer-1`, `implementer-2`) unless `--name` is given. A worker name is never reused while its record exists. After `seat archive` the name may be spawned again, and auto-numbering may reclaim it. |
| F4 | Only the lead or a caller outside the fleet may spawn, kill, archive, or resume seats, or review memory (section 6.2). |
| F5 | A seat's identity comes from an environment variable Foil sets when launching it. A seat can't claim another identity through any flag. This protects against mistakes by cooperating agents, not against hostile processes, and the documentation says so. |
| F6 | When a template asks for a worktree, spawning creates a git worktree on a new branch whose name is unique in the repository. Killing a seat never deletes its branch and never silently destroys uncommitted work. `seat archive` does not delete a branch and does not delete uncommitted work. |
| F7 | Foil writes nothing into the working tree. It creates no exclude entry. Files and worktrees it creates never appear as untracked or modified files in the user's repository. |
| F8 | Seat state is `alive` (its exact tmux window exists and its pane process is still running), `dead` (the window is gone, or the pane process has exited, and the seat wasn't killed), or `killed` (stopped with `foil seat kill`). Whether the pane process has exited is tmux's `#{pane_dead}` fact, not a reading of the pane. A seat window stays after its process exits, so the pane can still be read. |
| F9 | `seat resume` restarts `dead` seats, never `killed` ones. It launches with the harness and model recorded on the seat at its last launch, and with that harness's preset. It does not read the template's list to choose again, it does not apply fleet memory, and it does not overwrite the seat's harness or model. A new session id is not minted only because the template's first entry differs from the recorded harness. It uses the harness's own session resume when the preset supports it; otherwise it starts the seat fresh and tells it that it was restarted and should re-read its mail. A seat with no worktree resumes in the project directory. A seat that cannot be restarted is named in the error and does not stop the others. A killed name stays reserved until `seat archive`. A name that has been removed from `seats` is unknown, not killed. |

### Visibility

| ID | Requirement |
|---|---|
| F10 | `seat list` reports only facts Foil owns: each seat's name, template, state, and worktree, plus the harness and model the registry recorded at that seat's last launch, and its template's current description. That recorded pair is what resume launches (F9). Editing the template's harness list while the seat is alive does not change the pair `seat list` shows. The description is empty when the template is gone, the template cannot be read, or the persona cannot be read. A seat record with no `model` field loads that field as empty. |
| F11 | `seat peek` prints the raw last lines of one seat's pane, exactly as tmux captures them. It does this for an alive seat and for a dead seat whose window still exists and still carries this fleet's and this seat's markers, so a process that exited at launch leaves an error that can be read. A killed seat, a dead seat whose window is gone, or a stored window id that now names another window is an error. |
| F12 | Foil never parses, classifies, or interprets pane contents. Whether an agent is busy, idle, blocked, or done is stated by the agents themselves in board files. The operator, who is outside the fleet, may read a pane and send keystrokes only for an approval dialog: a folder-trust prompt, a login prompt, or a prompt that blocks the seat until a human or the operator approves it. That reading is the operator's. Foil does not scrape a pane, does not decide that a dialog is present, and does not send the keys. The operator does not send keys for anything else, and does not decide from a pane who is working or what they are working on. |
| F37 | `foil view` serves one read-only page for every project in this user's store on this host, outside the fleet only, so one viewer is enough for a machine. With a non-empty `FOIL_SEAT_ID` it prints `foil: view is outside the fleet only`, exits non-zero, and binds nothing. It needs no repository and runs from any directory. It lists each folder under `<root>/projects/` whose name is letters, digits, and `-`, that is not a symlink, and that holds `project.json`. A project opens only when its recorded checkout exists and resolves back to that same folder; otherwise it is listed by its recorded checkout, has no link, and its pages are a 404 that says to run `foil init` in it. A project's pages are under `/projects/<key>/`. It writes no file, sends no mail, writes no post, reviews no lesson, does not spawn, kill, archive, or resume, and types nothing into a pane. It binds `127.0.0.1` only. Without `--port` it binds the first free port from 7460 to 7509, moving on only when a port is in use, and fails with `foil: no free port in 7460-7509` when none is. `--port N` binds exactly N, an integer from 1024 to 65535, or fails with `foil: port N is in use` or `foil: invalid port`. Any other bind failure is `foil: could not listen on 127.0.0.1:N`. Its only stdout line is the page's address. Ctrl-C and SIGTERM exit 0 and leave seats, windows, the registry, and the board as they were. A failure of the command is one stderr line and a non-zero exit (N8). A failure inside one request prints nothing. It writes no access log. Apart from the tailnet name below, a request whose `Host` name is not `127.0.0.1`, `localhost`, or `[::1]`, or that has no `Host`, gets an empty 403, and a request with an `Origin` other than `http://` plus its own `Host`, including `null`, gets an empty 403. A request with a loopback `Host` that carries `X-Forwarded-For`, `X-Forwarded-Host`, `Tailscale-User-Login`, or `Tailscale-Funnel-Request` gets an empty 403, because `tailscale serve` sets those on every request it forwards and copies the client's `Host`. A method other than GET or HEAD gets an empty 405. It serves at most 64 connections at once and builds at most 8 pages at once; past that a request gets an empty 503. One page build gives tmux at most 10 seconds in total, and a tmux call still running then is stopped and counts as failed, so an abandoned request does not hold its build. The tailnet reaches the page only through `tailscale serve` in front of that loopback port, which keeps the request's `Host` and sets `Tailscale-User-Login` after deleting any value the client sent. At start, when `tailscale` is on `PATH` and `tailscale status --json` says Tailscale is running on a node with no tags, the view reads that node's MagicDNS name and its owner's login once. A request whose `Host` name is that MagicDNS name loads only when it carries exactly one `Tailscale-User-Login`, that value is the owner's login, it carries exactly one `X-Forwarded-Host` equal to its own `Host`, and its `Origin`, when present, is `https://` or `http://` plus its own `Host`. Anything else under that name gets an empty 403, including Funnel traffic, a tagged peer, a device of another user, and a login that is not ASCII. The view runs no `tailscale` command that changes anything, and never listens on a tailnet or LAN address. That check holds only for the HTTP and HTTPS forms of `tailscale serve` and `tailscale funnel`; the TCP forms forward raw bytes without those headers, and the README warns against them. The page is server-rendered, its links are plain links, and it has one nonce script. The Magic Patterns mock is a reference only; where it differs, this document wins. The page requests nothing from another host and refreshes nothing by itself. There is no auth on loopback: while it runs, any local user can read the page, including pane text and board bodies. |
| F38 | Every page has one header line of breadcrumbs (Foil, the project, then the fleet, seat, or the file). Settings is a link at the right end of that header and is not a breadcrumb. The footer is `This viewer does not type into a pane and does not decide progress.` The page opens on the project list, with the line `Every project in this user's Foil store on this machine. A project is one repository. Open one to see its fleets, settings, and seats.`, and for each project its name, recorded checkout, and fleet count. A project opens on its fleet list, with the line `One project shares roles, harnesses, and the default mapping. Each fleet has its own seats, board, posts, and overrides. Progress is status.md.`, each fleet's alive, dead, and killed seat counts and the modified time of its newest board file, and the project's lessons as `memory list --all` shows them. `/settings` is the global layer and needs no project. It shows the same rows project settings show, for the global layer. A row with no global file carries the `packaged` badge. A layer strip at the top of `/settings` and of a project's settings page reads Packaged, then Global, then Project, then Fleet. Each settings row has a source badge naming the layer that won for that row: `packaged`, `global`, `project`, or `fleet`. Project settings show the effective rows for that project: each role's description (the `roster list` rule), permission, and worktree, and each persona with no role; each eligible harness id (F27), whether its `command[0]` is on the `PATH` that `foil view` was started with and where it was found, its model ids, its launch argv with placeholders as written, and its `env` names, never their values; and each role's pair list as one card per pair, harness on top and model below, not two columns. An empty model shows `harness default`, with the tip that no `--model` is passed, so the CLI uses its own default. Under each role, a Rotation line lists the pairs in order. It does not number seats and does not mark a next seat. An argv token that looks like a credential, or that follows or holds a flag or name that does, is shown as `[hidden]`. That hiding is best effort. A fleet page shows, in this order: its seats, then `status.md`, then the posts, then the board files, then its overrides, attach command, and workspace. Seats are grouped: dead seats first under Needs attention, then alive seats under Running, then killed seats folded under Killed; inside a group the lead comes first, then by role and number. Each seat shows its name and description, its state, the harness and model recorded at last launch (F10), and its branch, plus a second line with the pair the next spawn of that role takes when an override changes it (F3). Links above the seats filter them by state, as `?state=alive`, `dead`, `killed`, or `all`; with none, killed seats are left out and counted, with a link to show all. `status.md` shows its first 15 lines, wrapped, and its modified time, with a link to open it whole. Posts are grouped by thread, the thread with the newest file first, and the other board files by folder, with each `mail/<seat>` its own group; each row shows the file's path below its group, its modified time, and its size. The fleet page's overrides section is titled Fleet overrides. The link is per role. It targets the project mapping when that role has project mapping rows, and `/settings` otherwise. When the fleet has no override rows, that section is one line: `None. Spawn uses each role's project pair list when that role has one, otherwise the global list.` Otherwise each pair is one card, harness on top and model below, an empty model shows `harness default` with the same tip, and a Rotation line per role starts from that fleet's stored seat count and marks the next seat. The rows' notes stay. A viewer-gap item other than these changes only when it is cheap and in the same code. The fleet shows `tmux attach -t '=<tmux_session>'` from its registry, or that it has no session yet, and the project's recorded checkout. A seat shows the same facts, links to the seats before and after it in the fleet's order, the attach command with `\; select-window -t <window id>` only when its window still carries this fleet's and this seat's markers, and the raw pane as `seat peek` prints it, 40 lines by default and at most 1280, with the time it was loaded, a Refresh link, and a link to its last line, or peek's one-line error and no pane text. The capture is not stored, logged, or classified (F12). Sections and column headers have an info icon that opens a short fixed explanation, listed under this table, which a click outside it, a scroll, or Escape closes. A modified time is relative, with the local time on hover. |
| F39 | A board file opens on its own page, `?open=<path>` on its fleet's page, only when it is in that fleet's listing, which skips symlinks, names that start with `.`, and names that are not UTF-8, and only when no part of its path is a symlink and it is a regular file. Any other path is a 404. The page shows the file's path, modified time, and size, a link back to its list on the fleet page, links to the files before and after it in the same group, and the first 1 MiB decoded as UTF-8, with invalid bytes replaced and long lines wrapped. A raw view serves the whole file's bytes as plain text that the browser does not run. A file over 16 MiB has no raw link, and its raw view is a 413 with one line. One unreadable fleet, list, or file is one line in its own section and leaves the rest of the page. |

The info explanations F38 names, one per section or column, exactly as the page serves them:

| Section | Explanation |
|---|---|
| Lessons | Project lessons. They outlive fleets and are copied into a seat at the next spawn or resume. States are proposed, accepted, rejected, and superseded. This is not the fleet override list. |
| Roles | A role is a description, a persona, a worktree flag, and a permission. The description is the first line of the persona. |
| Permission | auto asks the harness to skip approval prompts. ask stops the seat at its first approval prompt. |
| Worktree | yes means each seat of this role gets its own git worktree on a new branch, so its edits do not touch your checkout or other seats. Killing the seat keeps the branch. |
| Harnesses | How one agent CLI is launched, and the model ids its list names. Spawn does not refuse a model that is absent from the list. A file harnesses/<id>.toml replaces that one id. |
| Installed | Whether this viewer found the command on the PATH it was started with, and where. A seat looks the command up on the PATH of the foil command that launched it, so a viewer started elsewhere, such as a service, can differ. |
| Launch command | The argv foil runs to start a seat, with placeholders as written. A value that looks like a credential shows as [hidden]. |
| Default mapping | The shared default in mapping.toml: for each role, one ordered list of harness and model pairs, shown as pair cards. The rotation is on the pair, never on the harness or the model alone. An empty model shows harness default: no --model is passed, so the CLI uses its own default. Resume keeps the pair recorded on the seat. |
| Entries, in order | Each entry is one card, harness on top and model below. The next spawn of a role takes entry ((seats stored for that role, including killed) mod (number of entries)) + 1. |
| Attach | The session name stored for this fleet. The viewer does not type into the pane. |
| Workspace | The checkout recorded for the project. Every fleet on this repository shares it. Seat worktrees are separate branches. |
| Overrides | This fleet's overrides.toml. A role's entries, in order, replace the pair list below this fleet. The Rotation line marks the next seat from this fleet's stored count. An empty model is harness default. A model-only row on a multi-entry role is refused at spawn (F3). A running seat keeps its last launch. Resume does not read this file. |

## 6. Commands

### 6.1 Command reference

These are the only commands, subcommands, and flags. Every command also
accepts `--help`, and `foil --version` prints the version.

| Command | Flags | Behavior |
|---|---|---|
| `foil init [DIR]` | none | Checks that tmux and git exist and that DIR (default: current directory) is a git repository. Creates the project folder in the per-user store, the missing global default roles (F20), and `fleets/main/` (that fleet's board, posts, and registry). It writes no project settings, no persona, and no skill. It prints that folder's path. It writes nothing into the working tree and no exclude entry. When one stored project has the same origin remote, compared without HTTP userinfo, and its recorded path is gone, it adopts that record. A repository with no origin is matched the same way: exactly one store record whose recorded path is gone and whose repo identity matches this repository. The root commit is one such identity. Init adopts that record and prints which one. It adds no flag and no prompt. When several records match, it says so and adopts none. When no match is possible, it warns that an orphaned store record exists, names that record's path, and does not silently create a second empty project. A record is considered only when it could be this repository: the same root commit, or, for a repository with no origin, no root field and no origin of its own. A record for some other repository is ignored, including when this repository has no commits. The warning does not stop init. Adopt runs `git worktree repair` and, only after that repair succeeds, rewrites every absolute path in `run/registry.json`, `run/plans/`, `run/instructions/`, and `run/archive/` to the store paths, whatever the old absolute prefix was, including a repository directory that was renamed before init, and whether or not any seat has a worktree. The old prefix covers the old checkout, the old `.foil/` directory, and each seat worktree. The old `.foil/` prefix is read from a worktree's gitdir text before repair, by stripping `/worktrees/<label>`. The rewrite also matches a path that JSON stored with escapes. The same rewrite replaces a stale `FOIL_PROJECT` value stored in `run/plans/*.json` with the current project key, and that write is atomic (N7). ## 7. Data design

### 7.1 Layout

Everything for one project lives in one folder in a per-user store (F7).
The store root is `$FOIL_HOME` when that is set, made absolute so a
relative value does not follow a later working directory, otherwise
`$XDG_DATA_HOME/foil`, otherwise `~/.local/share/foil`. The project
folder is `<root>/projects/<key>/`. `<key>` is a readable slug of the
realpath of the Git common dir plus a short hash. The main checkout, a
linked worktree, and a seat worktree share that common dir, so they
share one folder. `project.json` records the main checkout, the origin
remote when there is one, without HTTP userinfo, the root commit when there is exactly one, and
the creation time. Init keeps a recorded
path that still exists. Otherwise it records the parent of the Git
common dir, including when init runs from a linked or seat worktree. After adopt or a
legacy move, and only after `git worktree repair` succeeds, absolute paths in `run/registry.json`, `run/plans/`, `run/instructions/`, and
`run/archive/` are rewritten to the store paths no matter
what the old absolute prefix was, including a repository directory that
was renamed, and whether or not any seat has a worktree. The old prefix covers the old checkout, the old `.foil/` directory, and each seat worktree. The old `.foil/` prefix is read from a worktree's gitdir text before repair. The rewrite also matches a path that JSON stored with escapes. A stale
`FOIL_PROJECT` value stored in `run/plans/*.json` is rewritten to the
current project key, and that write is atomic (N7). A failed repair leaves the stored paths unchanged. A later init maps the old store root or the old `.foil/` whenever that directory itself no longer exists. When the gitdir no longer names that store, the old folder is `<projects>/` plus the project key of the checkout recorded before the write. The check that its parent is gone applies only when rewriting the old checkout to the current one. The recorded checkout used for that retry is the path saved before this run writes the current checkout. A recorded checkout that no longer
exists is rewritten to the main checkout. A seat's environment
includes `FOIL_PROJECT` set to that key. It also includes `FOIL_HOME`
or `XDG_DATA_HOME` when the spawning process had that variable set, so
the seat resolves the same store. Every command resolves the project
the same way. `FOIL_PROJECT`, when it names a folder that has
`project.json`, selects that folder's recorded repository path.
Otherwise the command uses the Git toplevel of the working directory,
then the same key. The main checkout, a linked worktree, and a seat
worktree share the Git common dir, so they share the folder.
Global settings live at the store root. A project file is an optional
override. `<root>/star.json` stays one record for the store (F34). The concepts below
are fixed; exact names may vary.

```text
<root>/
  roles.toml                   the roles. init writes each missing default
  mapping.toml                 each role's pair list. init writes missing rows
  harnesses.toml               only harnesses someone changed
  harnesses/<id>.toml          one harness; beats the global list entry
  personas/<role>.md           only personas someone changed
  skills/operator.md           only when someone changed the skill
  projects/<key>/
    project.json               path, origin, root, created
    roles.toml                 optional whole-role overrides
    mapping.toml               optional whole-list overrides
    harnesses.toml             optional
    harnesses/<id>.toml        optional
    personas/<role>.md         optional
    fleets/<id>/               one fleet. FOIL_FLEET, default main
      overrides.toml           optional pair list for that fleet
      board/
        mail/<seat>/<time>-<from>-<rand>.md
        notes/                 unaddressed shared files
        room/<id>/<id>.md      room/v1 thread, and children beside it
        status.md              lead's status (status/v1)
        tasks/<id>.md          task/v1
        results/<id>.md        result/v1
      run/                     registry, archive, plans, instructions
        archive/<time>-<name>.txt
                               archived seat, prose, not in the registry
    memory/                    project lessons; survive fleets
    skills/                    directory stays. init does not write a
                               project operator skill. The lead and worker
                               skills are read from the package.
    worktrees/<label>          one directory per seat worktree
```

### 7.2 Template

`roles.toml` is the profile list. `mapping.toml` is the default harness and model list: one or more `[[map]]` rows per role, in spawn order (F3). `init` writes one global row per missing default role and omits `model`. Spawn reads that list (F3). There is no second harness string or model field beside it. Permission defaults to `auto`.

```toml
# roles.toml
[[role]]
id = "implementer"
description = "Implements the task on its own branch."
persona = "personas/implementer.md"
worktree = true
permission = "auto"

# mapping.toml
[[map]]
role = "implementer"
harness = "claude"

[[map]]
role = "implementer"
harness = "codex"
model = "gpt-6.1-sol"
```

A profile is one `[[role]]` row. Each mapping row is one `[[map]]` with `role`, `harness`, and an optional `model`. `roster add --from FILE` reads one document with `persona`, `worktree`, `permission`, and `[[harness]]` entries, and writes those into the two lists. That document is not stored.

| Field | Required | Meaning |
|---|---|---|
| `harness` | yes | Ordered `[[map]]` rows for that role. Each row has `role`, `harness` (a preset id, and a safe id), and optional `model` (passed to that preset's model option). An empty list, a row that is not a table, a missing or empty harness id, or a key other than `role`, `harness`, and `model` is invalid. |
| `persona` | no | Inline text, or a path to a Markdown file. |
| `worktree` | no, default `false` | Give each seat its own worktree and branch. |
| `permission` | no, default `auto` | `ask` or `auto`, mapped to the preset's flags. |

A role with one CLI is a list of one. `init` and `roster add` without `--from` write one entry and omit `model` when there is none. `model` omitted on an entry is empty.

### 7.3 Harness preset

| Field | Meaning |
|---|---|
| `id` | Preset name. |
| `command` | Launch argv. Placeholders: `{model}`, `{prompt}`, `{session_id}`. |
| `permission.ask`, `permission.auto` | Extra argv for each mode. |
| `resume` | Optional resume argv, using `{session_id}`. |
| `session_id` | `generated` (Foil creates a UUID and passes it at launch) or `none`. |
| `env` | Names of further environment variables to forward. A named variable takes its value from the tmux server's environment. `PATH` comes from the spawning caller. `PATH` and `HOME` are always forwarded (F26). |
| `models` | Ids this harness accepts. Informational. Spawn does not reject a model that is absent. An empty list names none. |

Built-in presets use each CLI's documented flags. A flag that could not
be verified is marked in the preset file.

### 7.4 Board files

**Mail:** Markdown with front matter `contract: mail/v1`, `from`, `to`,
`time` (UTC, ISO 8601), and an optional `re` (the mail file it answers),
followed by the body. Written atomically; file names never collide.
`foil send` does not write `re`.

**Room:** Markdown with front matter `contract: room/v1`, `from`, `time`
(UTC, ISO 8601), an optional `re` (the room file it answers), and `nudged`
(the seat ids typed to, sorted). There is no `generation` field. A waking
file's body starts with a short preamble, then the caller's text. A
decline's body is the line `decline` and its `nudged` list is empty.
Written atomically; file names never collide. Foil does not read these
fields to decide a later nudge.

**Contracts:**

| Contract | Front matter |
|---|---|
| `status/v1` | `state: working \| blocked \| done`, `updated`, `questions` (list, may be empty) |
| `task/v1` | `id`, `owner`, `state: open \| doing \| done`, `acceptance` |
| `result/v1` | `task`, `author`, `branch` (if any), `outcome: pass \| fail` |

**Checklist.** Once the lead has a plan, the `status/v1` body holds a
`## Checklist` of Markdown task items, one per line: `- [ ]` open,
`- [x]` done. An item starts with its task id when it has one.
`state: done` means every item is ticked. The front matter is unchanged.
Foil parses front matter only to print a file and does not act on contract fields (F16).

### 7.5 Foil-owned state

**Memory lesson** (schema-versioned): id, text, proposer, time, state
(`proposed`, `accepted`, `rejected`, `superseded`), reviewer, and an
optional `replaces`.

**Fleet overrides** (`fleets/<id>/overrides.toml`): zero or more `[[override]]` rows with `role`, an optional `harness`, a `model` that may be omitted only when `harness` is set, and an optional `note`. A role's rows, in order, are that fleet's list for the role, and spawn selects from it as it does from the mapping (F3). The workspace is the path in `project.json`. Posts are files under that fleet's `board/room/`. A caller inside the fleet writes rows with `roster update ROLE harness=ID/MODEL,ID/MODEL` or `model=VALUE`, and those rows always name a harness. A caller outside the fleet edits the global mapping, unless `--project`, which writes that role's whole project list. The lead instruction names the overrides file and says to re-read it before spawn. Spawn applies the selected row's model as the harness model flag. Resume does not read fleet memory (F9).

**Star record** (schema-versioned JSON, `<root>/star.json`, one per store): `shown`, the days a star line was printed; `minor`, the `X.Y` version at the last line; and `stop`, which the operator sets when the human declines (section 8, F34).

**Registry** (schema-versioned JSON): fleet id, tmux session, lead name,
and per seat: name, template, harness, model, tmux window id, state, worktree
path, branch, and session id. `harness` and `model` on a seat are the pair recorded at that seat's last launch. Resume keeps them (F9). A record written without `model` loads that field as empty. A new seat's entry is chosen from the seat records already stored for that role (F3). The schema version does not change. An archived seat is a prose file in `run/archive/`, not a registry key. Those files do not bump the schema.

An omitted permission is `auto`, and `roster add` without `--from` writes `auto`. `ask` is the explicit choice. The operator, outside the fleet, may set `permission` before the first spawn and again later. The next spawn picks it up. A live seat does not. Pair `auto` with a worktree stays. The operator may send keystrokes only for an approval dialog: a folder-trust prompt, a login prompt, or a prompt that blocks the seat until a human or the operator approves it. The operator does not send keys for anything else. An update dialog, a first-run dialog, and an opt-in are reported to the human and not answered. Foil does not scrape or interpret the pane to decide that the dialog is there. A prompt the operator will not approve is reported to the human with the seat name and what the pane shows, and is not answered. The operator refuses a suspicious prompt by not sending the keys and by telling the human. It does not send a denial sequence unless that sequence is the approval dialog's own reject key, and it says so to the human first. The command is `foil roster update ROLE permission=VALUE`. When the init report has the `For the human:` star line (F34), the operator tells the human that line once, after the goal, not the first-run check, reaches `state: done`. The line is not an instruction to the operator. The operator never stars, opens a browser, or runs `gh` or an API for the human. When the human declines or says they already starred, the operator sets `"stop": true` in `star.json` in the store root, two levels above the project folder, and does not raise it again. A standing instruction from the human not to mention it is followed the same way. |

The seat follows the task file, not a second copy of the brief in the mail body. Wait for that seat's mail or result file. `foil send` one seat when the point is for that seat alone: a question or a correction. `foil post` when more than one other seat needs the same point. How to manage the roster: the lead may set `harness` and `model` only, with `foil roster list`, `foil roster show`, and `foil roster update`. ## 10. Verification

Principle: **real Foil, real tmux, real git, a small real task; only the
agent is replaced.** Tests check real outcomes (tests pass, a branch
exists, a window is gone), not Foil's reports about itself.

**Fake harness** (the `fake` preset) is a test double for an agent CLI:

- It runs interactively in its pane and reads typed lines, like a real TUI.
- When a nudge arrives, it reads the file the nudge names. That file may be mail or a room file. A decline types nothing, so the double sees no line for that write.
- It follows a per-seat script, in a format the standard library can
  parse. Reactions include running a shell command (for example
  `foil seat spawn`, `git commit`, the fixture's test runner), writing a
  board file, and `foil send`.
- On start it handles any mail it hasn't handled yet, so restarts work. It does not scan `board/room/`.
- It keeps a debug log; tests never assert on it.
- It launches through the normal preset path, so templates, launch,
  environment, instruction files, worktrees, and nudges are exercised
  exactly as with a real CLI.

**Required scenarios** (each is a fixture repository plus seat scripts;
the test plays the operator):

| # | Scenario | Assert |
|---|---|---|
| 1 | Happy path: the fixture has one failing test. The test runs `init` and `seat spawn lead --task "make the tests pass"`. The lead spawns an implementer and a reviewer; the implementer commits a fix on its branch; the reviewer runs the tests there and approves; the lead merges and sets `status.md` to done. | Tests pass on the merged result; the branch is merged; `status.md` says done; `seat kill --all` leaves no Foil windows. |
| 2 | Authority: a worker tries `seat spawn` and `seat kill lead`. | Both fail; the fleet is unchanged. |
| 3 | Crash: kill the tmux server mid-scenario, then `seat resume`. | Scenario 1's outcome is still reached. |
| 4 | Operator loop: the lead writes a question to `status.md`; the test answers with `foil send lead`. | The lead's final status reflects the answer; `seat peek lead` shows raw pane text. |
| 5 | Memory: a worker proposes a lesson and fails to accept it; the lead accepts it. | A seat spawned afterwards has the lesson in its instruction file; `memory list` shows it accepted. |
| 6 | Errors: send to an unknown seat, spawn a missing template, run outside a git repository. | Each gives a one-line error and a non-zero exit, with no traceback. |

**Standing checks:** the command surface matches section 6 exactly; the
package source size is reported against the N4 target; tmux window identity, atomic
writes, public-safety checks (N9), and the documentation index check (D8)
pass.

**Live tier (optional):** the same scenarios with real harness CLIs in
place of `fake`, judged by the same assertions. It needs authenticated
CLIs, so it's opt-in and excluded from the default test run.

## 11. Out of scope

- Any command, subcommand, or flag not in section 6. Changing the command
  surface requires changing this document first.
- Parsing or interpreting pane contents. The only exception is the operator, bounded by the F12 replacement. Foil still does not do it.
- Remote machines and Windows. A project is one copy of the code. Several fleets may run on it. They share the effective roles, harnesses, and mapping. Each fleet has its own board, posts, registry, and an optional pair-list override. Seat worktrees stay in the same Git repository.
- A UI or server other than `foil view`; a viewer that writes, or types into a pane; a daemon mode, or a command that installs a service; MCP; or a hosted service.
- Message read receipts, usage-based dispatch, and persona catalog tools beyond `roster list` of the personas `init` copied. Usage-based dispatch includes quota detection, probes, pacing, credential rotation, and switching a running seat because it looks exhausted. Spawn-time rotation across the ordered harness list on a role is in scope. A spawn selects `entries[n % len(entries)]`, where `n` is the number of seat records already stored for that role (F3). That spreads later worker spawns across the entries the role was given. It does not balance usage and it does not move a seat that is already running.
